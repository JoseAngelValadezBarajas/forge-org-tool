# FORGE Org Tool 1.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the simplified, local-first FORGE Org Tool 1.0 while preserving compatible user data, product contracts, and the supported Project Transfer workflow.

**Architecture:** Keep React/Vite/TypeScript, FastAPI, SQLite, Tauri 2, npm workspaces, and OpenAPI. Retire advanced product capabilities from active UI/API while retaining their legacy tables and data during forward-only migration; new databases contain only the active 1.0 schema. Keep durable state in SQLite behind application/domain boundaries, with a shared validated transfer engine and capability-oriented frontend.

**Tech Stack:** React, TypeScript, Vite, FastAPI, Pydantic, SQLite, Tauri 2, npm workspaces, OpenAPI, Playwright, pytest.

**Spec:** `docs/product/mvp-1.0.md` (transcribed from the user-approved FORGE Org Tool 1.0 implementation prompt).

## Global Constraints

- Preserve React/Vite/TypeScript/FastAPI/SQLite/Tauri 2/npm workspaces/OpenAPI.
- Preserve existing user data; do not seed production data or modify operator databases during tests.
- Existing databases must receive a verified SQLite-consistent backup before schema changes; migrations are forward-only, replay-safe, and reject future versions safely.
- New databases must not create obsolete advanced-capability tables.
- Keep Project Transfer, Planning Tasks, Acceptance Criteria, Dependencies, and shared packages.
- Desktop IPC must not expose process, port, shell, arbitrary URL, credentials, or unrestricted filesystem access.
- Keep `/__components` development-only and maintain the Apache-2.0 project licensing.
- Do not archive original FORGE, merge PR #1/#2, force-push, or change global Figma variables.

## Review Focus

- Existing database upgrade interrupted after backup: reopen must retain original DB integrity and complete or retry safely.
- Existing database at a future schema version: startup must refuse mutation with a useful, non-destructive error.
- Import with stale fingerprint, cross-workspace references, duplicate IDs, malformed attachment archive, or oversized image: reject atomically with no partial writes.
- Legacy records in retired tables: remain preserved but absent from active routes and new-database schema.
- Concurrent status updates and restart: one authoritative SQLite status survives reload without client-only divergence.
