# FORGE BYOC 0.1 Design

## Intent

Add `Settings > Storage` with local SQLite as the default and an explicitly configured, user-owned Supabase project as an online provider. An authenticated user can use the first vertical slice—Workspace, Project, Epic, Story/Bug creation and status changes—from more than one installation. FORGE does not own, provision, copy, or migrate the user's cloud data.

## Goals

- Keep the current local FastAPI + SQLite + Tauri sidecar path unchanged by default.
- Accept only a hosted Supabase project URL and `sb_publishable_*` key; never accept or persist a database password, service-role key, or secret key.
- Authenticate through Supabase Auth, refresh sessions in memory/session storage, and never log tokens or passwords.
- Use the Supabase Data API over HTTPS with the signed-in user's JWT; never expose PostgreSQL directly from an installed client.
- Require a successful schema/version/permission preflight before showing Supabase as `ready`.
- Put membership authorization and non-bypassable rules in owner-applied SQL constraints, functions, grants, and RLS.
- Provide deterministic adapter tests and an explicit manual validation step when no real Supabase project is available.

## Non-goals

- Offline sync, conflict resolution, realtime, attachments in cloud storage, automatic local-to-cloud transfer, Firebase, or Android certification.
- Running provisioning SQL from FORGE or asking the installed app for admin credentials.
- Rewriting unrelated SQLite repositories or changing existing imports/exports.

## Anti-goals and invariants

- Do not touch a production or operator database.
- Do not silently fall back to SQLite after a cloud request fails.
- Do not move, duplicate, merge, or delete data when changing providers.
- Do not alter `main` or merge a pull request automatically.
- Do not distribute privileged credentials.

## Current architecture findings

- `apps/api/src/forge_org/api/dependencies.py` constructs services from `sqlite3.Connection`, and `connection.py` treats `FORGE_DATABASE_PATH` as a filesystem path. A PostgreSQL URL cannot be substituted there.
- `packages/api-client` already has capability modules and a stable `organizationApi` facade, but its transport is fixed to same-origin FastAPI requests.
- The web application already has `/workspaces/:workspaceId/settings`; the storage panel will live there without changing existing workspace/tag behavior.
- Tauri starts the Python sidecar and has an explicit CSP. Supabase HTTPS must be added to `connect-src`; the sidecar remains local and does not receive PostgreSQL credentials.

## Approaches considered

### A. Client-side Supabase Data API adapter — selected

Keep the local transport and add a runtime-configurable Supabase transport in `@forge-org/api-client`. Auth and Data API calls use HTTPS, the user JWT, and the publishable key. This matches the trust boundary: an installed client is not privileged, and RLS must authorize every request. It limits the implementation to the requested vertical slice without rewriting all SQLite services.

### B. FastAPI sidecar proxy for Supabase — rejected for 0.1

The sidecar could proxy every cloud request, but it is still user-controlled and would need a secure per-request profile/session bridge. It would add a second authorization boundary and make a local process appear more trusted than it is, while requiring a broader backend repository refactor.

### C. PostgreSQL driver in the desktop application — rejected

This would expose a direct database connection boundary, require distributing database credentials, and conflict with the requirement that installed clients use the Supabase Data API and owner-managed RLS.

## Chosen boundary

`@forge-org/api-client` owns provider selection, profile validation, Supabase Auth session refresh, and the narrow remote capability adapter. Local capability functions continue to call the existing FastAPI routes. The remote adapter implements the existing response shapes for Workspace, Project, Epic, Feature, and planning overview; unsupported non-vertical-slice capabilities return an explicit error instead of falling back locally.

The owner-run SQL migration creates the first cloud schema and `forge_create_workspace` / `forge_storage_preflight` functions. Direct membership creation is not granted to clients. Project, Epic, Feature, and status writes are protected by membership-aware RLS policies and constraints.

## Session and configuration lifecycle

1. Local is the initial provider and is reported as ready without network access.
2. Supabase profile validation is pure and rejects malformed URLs, non-HTTPS hosts, query/fragment/userinfo, and non-publishable keys.
3. The user signs in with Supabase Auth. Passwords are used only for the request and discarded.
4. The access/refresh session is kept in memory/session storage for the running browser/WebView; configuration contains only the project URL and publishable key. Desktop restart can require sign-in again; no token is written to logs or the repository.
5. Every remote request refreshes an expired session before sending the JWT. A missing/invalid session is an authentication state, not a reason to use SQLite.
6. `ready` is shown only after Auth, the expected schema version, and the preflight RPC succeed.

## Verification boundary

Without a user-supplied disposable Supabase project, automated tests use mocked HTTPS responses and SQL/static contract checks. The delivery notes will state the real-project validation as one manual owner action, not as completed evidence. No live credentials are committed or inferred.
